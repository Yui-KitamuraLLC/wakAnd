# AES-GCMへの変更検討案

2026-10-14 JST。設計検討用。現行のoauth-design.mdや本番暗号方式を置き換えていない。
PHP 8.2.32/8.3.32 CGIの実測でsodium=false、extension_dir内のsodium.soも読取不可。
OpenSSL拡張とaes-256-gcmの利用可否・動作は、本番で別途確認が必要。

## 候補と成立条件

PHP OpenSSLのAES-256-GCMを候補とする。256ビットの専用乱数鍵、96ビットIV、128ビット認証タグを使用する。
鍵は厳密に32バイトへ復号してからAPIへ渡す。PHPによる短い鍵のゼロ埋め・長い鍵の切り詰めを許可しない。
OPENSSL_RAW_DATAを使用し、暗号化失敗・タグ長不正・復号失敗・JSON不正を503へまとめ、値や例外詳細を出さない。
特にopenssl_decryptは呼出側でタグ長を確認する必要があるため、16バイト以外のタグを渡さない。

AADは現行のenvironment/link_id/generation/key_idの結合を保持し、暗号形式の固定識別子も追加する。
他行・他世代・他環境・他形式の差し替えを拒否する。平文保存、CBCへのfallback、認証タグ省略は行わない。

## IVの一意性を保証する案

GCMでは同じ鍵とIVの再使用を避ける必要がある。現行の24バイト乱数nonceを12バイトへ短くするだけの変更にしない。
第一候補は、鍵ごとの永続的な単調増加カウンターから96ビットIVを構成する方式。
32ビットの固定フィールドと64ビットのカウンターを固定バイト順で連結し、同じAES鍵を他用途・他環境で共有しない。
各暗号化で新しい値をDBの独立接続から原子的に予約・commitし、失敗や外側transaction rollbackでも返却しない。
上限到達・カウンター行欠落・DB障害では暗号化を拒否する。起動時に0へ戻したり、キーIDだけ変えて同じ鍵を再登録したりしない。
DB復元時は、同じ鍵で暗号化を再開する前に新しいAES鍵とカウンターへ切り替える運用が必要。

この案は専用のカウンター保存先を必要とする。追加テーブルを含む002更改とRepositoryのversion照合は、
設計の採否決定後に用意する。001の再作成・DROP・本番への自動DDLはしない。適用は管理者が行う。
現行4テーブルだけで実装できるという前提にはしない。

## 鍵と暗号文の移行

- AES用には新しいキーIDと32バイトの専用鍵を用意する。生成済みv1鍵やrate limit鍵を上書き・転用しない。
- token_bundleはMEDIUMBLOBなので、形式識別子・IV・タグ・暗号文を格納できる。形式識別子もAADで認証する。
- キーIDと形式の対応を明示管理し、旧XChaChaの先頭乱数を新形式と推測して復号しない。
- 旧形式の行があるかを秘密非表示で確認する。旧暗号文をAESへ直接読み替えたり、エラー回避のため削除したりしない。
- 旧形式がある場合はsodium利用可能な管理環境での限定移行、または失効・再連携の手順を別途設計する。
- maintenance=trueで配置・管理者更改・診断を行い、既存client_secret/DBパスワード/端末設定を保持する。

## 実装前に確定するもの

1. 本番OpenSSLとaes-256-gcmの利用可否。秘密を使わないメモリ内round tripと不正タグ拒否を確認する。
2. カウンター方式・002更改・鍵生成とバックアップ/復元手順の採否。
3. 既存暗号文の有無と移行方針。本番鍵の追加は管理者が明示承認した後に行う。

## 必要な検証

既知のGCMテストベクトル、鍵/IV/タグ長、改ざん・短いタグ・AAD/行/世代/環境の差し替え、未知形式・未知キーIDの拒否を確認する。
独立MySQLで並列IV予約、process再起動、外側rollback後の非再使用、上限/行欠落/障害での拒否を検証する。
既存OAuthの交換/応答喪失/更新/解除/遅延成功の競合試験も新Cipherで通す。
旧形式を含む移行とDB復元は別の検証対象とする。暗号化のround tripだけで移行・実OAuth完了とは扱わない。
